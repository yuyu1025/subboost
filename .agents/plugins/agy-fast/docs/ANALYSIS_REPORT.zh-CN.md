# Antigravity 任务执行延迟分析报告与优化方案（脱敏版）

> **数据脱敏说明**：本报告基于真实开发环境中采集的脱敏运行轨迹与汇总统计数据编制。所有个人目录路径、账号信息、私有仓库名称、代码片段与日志明细均已移除，仅保留聚合统计指标、延迟分布与可复现的验证方法。

## 1. 研究背景与数据样本

在实际工程任务中，即使大语言模型自身的文本生成速度（每秒输出词元数，TPS）达到 250 tok/s 以上，一个完整的多轮代码修改任务仍常常需要数分钟甚至十几分钟。为定位真实耗时来源，我们在严格遵守 Antigravity 官方使用政策的前提下，对脱敏后的历史运行轨迹和底层事件日志进行了定量统计。

### 1.1 样本规模

| 数据类型 | 样本规模 | 统计内容 |
| :--- | :--- | :--- |
| 会话轨迹汇总（`transcript.jsonl`） | **55 个真实会话**，涵盖 **8,446 轮**模型调用、**17,302 次**工具调用、**103 个**完整多轮任务 | 端到端活跃耗时、轮次分布、工具批量大小、有效吞吐量与提示词缓存命中率 |
| 完整未截断轨迹（`transcript_full.jsonl`） | **38 个完整会话**（含 25 个全量字段深度子集） | 按操作类型的耗时分布、工具返回字节体积、重复读写模式、工具失败率与命令分类 |
| 毫秒级运行事件日志 | **100 轮**主模型 HTTP 请求、**129 次**远端安全评估请求、**397 次**本地安全检查记录、**73 组**连续文件编辑间隔 | 网络往返延迟、首字等待时间（TTFT）、单次工具审查耗时与本地磁盘写入耗时 |
| 本地运行时冷启动测试 | 5 种常用运行时各 **10 次**冷启动采样（macOS Apple Silicon 环境） | `rg`、`sh`、`zsh`、`python3`、`node` 的进程启动延迟 |

- **总活跃时间**：55 个会话合计 239,461 秒（66.52 小时，已剔除用户输入停顿）。
- **纯单 Agent 活跃时间**：进一步剔除等待人工确认或等待多 Agent 返回的阻塞步骤（如 `ask_question`、`swarm_wait`、`schedule`、`manage_subagents`）后，共计 **198,902 秒（55.25 小时）**。
- **单任务基线（103 个多轮任务）**：
  - 中位数：**19 轮**模型调用 / **40 次**工具调用 / **8.9 分钟**
  - 均值：**39.4 轮**模型调用 / **79.2 次**工具调用 / **17.6 分钟**
  - P90：**124 轮**模型调用 / **230 次**工具调用 / **53.2 分钟**

## 2. 端到端耗时构成

### 2.1 单 Agent 活跃时间拆解（198,902 秒）

一个完整多轮任务的总耗时可以拆解为以下 5 个环节：

| 耗时环节 | 估算耗时（秒） | 占比 | 测量依据 |
| :--- | ---: | ---: | :--- |
| 每轮主模型首字等待时间（TTFT 固定开销） | 49,883 ~ 64,593 | **25.1% ~ 32.5%** | 8,218 轮 × 实测中位 `6.07s` / 均值 `7.86s` |
| 模型思考与参数解码 | 84,509 ~ 99,219 | **42.5% ~ 49.9%** | 总输出 10,874,534 output tokens |
| 多工具批处理流式缓冲等待 | 19,475 | **9.8%** | 同轮第 1 个到最后 1 个工具创建的时间差 |
| 工具执行：云端安全评估（串行） | ~12,001 | **6.0%**（占工具阶段 **39.6%**） | 约 7,454 次触发 × 均值 `1.61s` |
| 工具执行：本地磁盘、编译、测试与外部命令 | ~18,324 | **9.2%**（占工具阶段 **60.4%**） | 实际工具运行耗时 |
| **合计（纯单 Agent 活跃时间）** | **198,902** | **100.0%** | **单 Agent 有效吞吐 54.7 tok/s（含等待总活跃 239,461s 为 45.4 tok/s）** |

| 操作类型 | 轮次数 | 工具调用数 | 模型耗时（秒） | 流式等待（秒） | 工具执行（秒） | 合计（秒） | 剔除多 Agent 协调后占比 |

## 3. 发现的 6 个主要问题

### 问题 1：每轮存在约 6~8 秒的首字等待下限，短输出轮次拉低整体效率

按单轮 `output_tokens` 对 8,446 轮请求分组后，有效吞吐量呈现明显的长度依赖：

| 单轮输出词元数区间 | 轮次数（占比） | 均值输出（tok） | 耗时中位数（秒） | 耗时均值（秒） | 实际有效 TPS |
| :--- | ---: | ---: | ---: | ---: | ---: |
| `0 - 100` | 788（9.3%） | 76 | 8.0 | 16.8 | **4.5** |
| `100 - 300` | 2,747（32.5%） | 189 | 8.0 | 13.0 | **14.5** |
| `300 - 700` | 2,214（26.2%） | 452 | 9.0 | 12.2 | **37.0** |
| `700 - 1500` | 1,078（12.8%） | 1,017 | 13.0 | 18.0 | **56.6** |
| `1500 - 4000` | 940（11.1%） | 2,469 | 17.0 | 25.2 | **97.9** |
| `4000+` | 679（8.0%） | 8,185 | 38.0 | 52.7 | **155.2** |

毫秒级日志显示：
- 同一 API 域名的轻量审查请求 HTTP 响应头耗时中位数为 **0.90 秒**，说明基础网络往返延迟低于 1 秒。
- 主模型从上一步工具结束到收到 HTTP 响应头（TTFT）的中位数为 **6.07 秒**（均值 **7.86 秒**，P90 **14.67 秒**），而后续流式输出到开始执行首个工具的中位数仅为 **1.61 秒**。
- **68.1%** 的轮次输出少于 700 tokens。在中位数轮次中，约 **79%** 的模型阶段时间用于等待首字节响应，只有约 **21%** 处于文本解码阶段。

**结论**：减少总轮次数对缩短任务总耗时的作用，远大于单纯提升模型每秒解码速度。

### 问题 2：工具调用串行执行且每次编辑/Shell 命令均触发远端审查

Antigravity 在工具执行前会先运行本地规则检查（耗时 10~80 微秒）；未命中本地白名单的调用会同步阻塞并向远端轻量模型发送风险评估请求：

- 在毫秒级日志的 231 次工具调用中，**53.2%（123 次）** 触发了远端审查：其中 `edit_file` 触发率 **100%**，`run_command` 触发率 **92.9%**；内置 `read_file` 命中本地白名单，无需远端审查（连续读取间隔中位数 **6.69 毫秒**）。
- 单次远端审查的中位阻塞耗时为 **1.57 秒**（均值 **1.61 秒**，P90 **1.97 秒**），每次需上传 **26 ~ 47 KB** 的格式化历史记录；而 `edit_file` 在本地磁盘上的实际修改耗时中位数仅 **43.47 毫秒**。
- 对 137 次审查时间戳做并发重叠统计，最大并发数为 **1**（重叠次数为 **0**），说明同轮发出的多个工具调用按顺序逐个完成审查与执行。

同轮批量调用时的实测执行耗时（中位数）呈线性增长：

| 同轮批量次数 | `read_file`（秒） | `edit_file`（秒） | `write_file`（秒） |
| :---: | :---: | :---: | :---: |
| 2 次 | 0.0 | **4.0** | **4.0** |
| 3 次 | 0.0 | **6.0** | **7.0** |
| 4 次 | 0.0 | **7.0** | **8.5** |
| 5 次 | 0.0 | **9.0** | **10.0** |
| 6+ 次 | 0.0 | **14.0**（均值 18.2） | **9.0** |

### 问题 3：多工具批处理需等待整轮流式输出完毕才开始执行

当模型在一轮内连续输出多个工具调用时，客户端会等所有工具参数流式接收完毕后，才开始执行第 1 个工具。

- 在 55 个会话中，这一等待累计消耗 **19,475 秒（占单 Agent 活跃总时间 9.8%）**。
- 在 `code_edit` 类别中，流式等待占该类别总耗时的 **31.5%**（当同轮包含 6 次及以上 `edit_file` 时，流式等待中位数达 **17.0 秒**，随后的串行执行又耗时 **14.0 秒**）。

### 问题 4：工具接口粒度偏细导致轮次增加与编辑被重复拆分

1. **连续单工具调用链**：全部工具轮次中有 **51.7% ~ 53.9%** 每轮仅调用 1 个工具。在 38 个完整会话中，仅 `read_file`（368 轮）和 `run_command`（271 轮）的连续单调用链就产生了 **639 个**本可合并的额外轮次。
2. **`edit_file` 单块限制**：内置 `edit_file` 每次只能修改一处连续代码块。在 2,463 次 `edit_file` 调用中，**1,293 次（52.5%）** 是同一轮内对同一个文件发起的额外拆分调用；在 25 个会话子集中，**42.1%** 的被编辑文件需要 3 次及以上独立调用。同时 `edit_file` 失败率仅为 **1.0%**，说明开销主要来自接口拆分，而非编辑匹配失败。
3. **只读搜索被迫走 Shell**：在 1,629 次 `run_command` 调用中，**42.2%（688 次）** 是 `rg`/`grep`/`find`/`ls`/`sed` 等只读检索，**4.1%（67 次）** 是 `git status`/`diff`/`log`/`show` 等只读仓库查询，合计 **46.3%**。本机实测 `rg` 冷启动仅 **2.1 毫秒**，但通过 `run_command` 执行的中位耗时达 **2.0 秒（均值 2.6 秒）**。
4. **会话启动探索耗时**：38 个会话的前 3 轮平均消耗 **49.2 秒**，主要集中在查看目录结构、git 状态和构建/测试脚本。

### 问题 5：整文件读取导致上下文体积增大并拉长首字等待时间

统计 38 个完整会话中工具写入历史上下文的总字节数（合计 **55.67 MB**）：

| 工具 | 返回总字节数 | 占比 | 调用次数 | 单次均值 | ≥10 KB 大返回次数 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| `read_file` | **45.60 MB** | **81.9%** | 4,838 | 9,425 B | **1,568 次（31.41 MB）** |
| `run_command` | 6.01 MB | 10.8% | 1,629 | 3,691 B | 237 次（2.45 MB） |
| `webview_browser` | 1.72 MB | 3.1% | 135 | 12,755 B | 72 次（1.29 MB） |
| 其他工具合计 | 2.34 MB | 4.2% | — | — | — |

- 在 25 个会话子集中，存在 **1,383 次**对同一文件的重复读取（其中 **438 次**因 800 行/45 KB 截断导致连续分段读取）。
- 样本中有 **69.4%** 的轮次上下文超过 150k tokens（**37.5%** 超过 300k tokens）。仅看输出小于 300 tokens 的短轮次（排除解码差异），上下文在 0~30k 时中位耗时 **7.0 秒（均值 7.2 秒）**，超过 150k 后升至 **9.0 秒（均值 13.2~14.1 秒）**。

### 问题 6：工具阶段过长引发提示词缓存失效并进一步拉长下一轮耗时

在 5,067 次相邻轮次转换（上轮上下文 >25k tokens，剔除主动上下文压缩）中，共有 5,024 次具有有效时间间隔；按间隔分组统计缓存命中率下降超过 50% 的事件（共 252 次）：

| 相邻两轮时间间隔 | 失效次数 / 总转换数 | 缓存失效率 |
| :--- | ---: | ---: |
| `< 60 秒` | 62 / 4,468 | **1.4%** |
| `60 - 180 秒` | 60 / 377 | **15.9%** |
| `180 - 300 秒` | 15 / 43 | **34.9%** |
| `300 - 600 秒` | 24 / 39 | **61.5%** |
| `>= 600 秒` | 91 / 97 | **93.8%** |

在短输出轮次（<500 tokens）中，缓存命中时中位耗时 **7.0 秒**，缓存失效时升至 **10.0 秒（+3.0 秒）**。串行工具调用耗时越长，两轮间隔越容易超过 60 秒，进而触发下一轮缓存失效和更长的首字等待。

## 4. 合规边界与 `agy-fast` 解决方案

### 4.1 政策合规原则

`agy-fast` 完全遵循 Antigravity 官方插件与使用政策：
- **不绕过、不禁用、不拦截**任何内置安全检查机制；
- **不修改**客户端安装目录或二进制文件；
- 仅使用官方文档定义的原生扩展能力：`plugin.json`、`mcp_config.json`（本地 Stdio MCP 服务）、`hooks.json`（仅注册 `SessionStart`）与 `rules/AGENTS.md`。

### 4.2 问题与解决方案对照表

| 发现的问题 | `agy-fast` 对应方案 | 技术实现要点 |
| :--- | :--- | :--- |
| 问题 4：46.3% 的 `run_command` 为只读搜索与 git 查询，且连续单命令轮次多 | **`batch_search`（MCP 工具 1）** | 单次调用接收最多 20 条混合查询（`text`、`regex`、`glob`、只读 `git`），进程内 `Promise.all` 并发执行；优先调用本地 `rg`（2.1ms 启动），无 `rg` 时自动回退 Node.js 并发遍历；对 `git` 实施严格只读白名单与参数校验；统一按字符预算截断。 |
| 问题 2、3、4：52.5% 的 `edit_file` 为同轮同文件拆分，触发线性串行审查与流式等待；编辑与校验分离 | **`apply_edits`（MCP 工具 2）** | 单次调用完成单文件多处或跨文件修改，支持指定行号范围、保留 CRLF 换行、保留文件权限与软链接；先在内存中校验全部匹配与重叠冲突（全部通过才写入磁盘，任一失败则 0 文件修改）；支持可选内联 `verify` 命令，修改完成后立即校验并返回精简结果。 |
| 问题 5：`read_file` 占工具返回体积 81.9%，引发大上下文与重复分段重读 | **`read_slices`（MCP 工具 3）** | 一次调用同时支持提取多语言顶层符号大纲（TS/JS、Python、Go、Rust、C/Java/Kotlin/C#/Swift、Shell、Markdown、JSON/YAML 的起止行号）和批量按精确行段读取多文件片段；内置总字符预算。中小整文件（<300 行）继续沿用本地白名单内置 `read_file`。 |
| 问题 2、4、6：构建/类型检查/测试多条命令串行运行且输出冗长 | **`run_checks`（MCP 工具 4）** | 在本地并发池中同时执行多项检查命令并控制超时；默认 `compact` 模式在命令通过时仅输出 1 行摘要，失败时清除 ANSI 控制符并提取报错行及尾部日志。 |
| 问题 4：会话前 3 轮平均消耗 49.2 秒用于初始目录与状态探索 | **`SessionStart` 一次性快照钩子** | 会话启动时运行单文件脚本（实测耗时约 35~50ms），注入不超过 1.5 KB 的仓库结构快照（git 分支、未提交修改、最近 3 条提交、2 层目录树、构建脚本清单）。位于会话最前端，后续轮次持续命中提示词缓存。绝不注册 `PreToolUse`/`PostToolUse` 以避免每步额外延迟。 |
| 问题 1、4：单工具串行轮次过多，且延迟加载 MCP 工具首次需额外读取 schema 文件 | **精简 4 工具 + `rules/AGENTS.md` 内联参数签名** | 仅暴露 4 个合并操作工具（`agy-fast_fast`），并在约 2.2 KB 的 `rules/AGENTS.md` 中直接提供 4 个工具的简明参数签名与调用路由，使模型首轮即可直接调用 `call_mcp_tool`，免去先读 `.json` 定义文件的额外轮次。 |

### 4.3 技术栈选择依据

基于冷启动基准测试（macOS Apple Silicon 实测 `node` 17.7ms、`rg` 2.1ms；Windows 下 `CreateProcess` 加载 PE/DLL 约 80~250ms、`powershell.exe` CLR 冷启动可达 1.5~3s，常驻服务与批处理在 Windows 上收益更显著）与分发易用性对比，选择 **TypeScript（strict 模式）+ `esbuild` 打包为独立零依赖 ESM（`.mjs`）+ Node.js >= 20**：
- **零 `node_modules` 安装体验**：构建产物直接随仓库分发，用户克隆或一键安装后无需编译、无需执行 `npm install`，跨 macOS / Linux / Windows 通用。
- **常驻低延迟**：MCP Stdio 服务在会话期间常驻运行，进程间通信耗时低于 1 毫秒。
- **易于审计**：不混淆打包产物，所有源码与打包文件均公开可读。

## 5. 预期收益与可复现验证方法

以 55 个会话的单 Agent 基线（均值 39.4 轮 / 79.2 次工具调用 / 17.6 分钟）为参照：

| 指标 | 基线实测 | 启用 `agy-fast` 预期改进方向 |
| :--- | :--- | :--- |
| 会话前 3 轮探索耗时 | 均值 49.2 秒 | 降低 40% ~ 65%（由启动快照替代初始目录和 git 探索） |
| 编辑阶段工具调用次数 | 均值 3.71 次/轮（52.5% 同文件重复拆分） | 降低 60% ~ 75%（多块跨文件合并为单次 `apply_edits`） |
| 只读搜索类 Shell 调用 | 占 `run_command` 的 46.3% | 降低 65% ~ 80%（由 `batch_search` 替代） |
| 任务总模型轮次数 | 均值 39.4 轮（中位 19 轮） | 降低 35% ~ 50% |
| 相邻两轮间隔 >60 秒的比例 | 11.1%（556 / 5,024 次转换） | 明显降低，从而减少提示词缓存失效 |

### 使用内置脚本自行复现测量

项目自带离线分析与对比工具 `dist/benchmark.mjs`，可直接解析标准 `transcript.jsonl` / `transcript_full.jsonl`（纯本地运行，不上传任何数据）：

```bash
# 分析单组轨迹、本机全部历史轨迹或最近 10 个本地会话
node dist/benchmark.mjs analyze /path/to/transcripts
node dist/benchmark.mjs analyze --local
node dist/benchmark.mjs analyze --local --recent 10

# 对同一任务在启用插件前后的轨迹做 A/B 指标对比
node dist/benchmark.mjs compare --before ./before/transcript.jsonl --after ./after/transcript.jsonl
```
